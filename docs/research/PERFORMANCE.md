# S7 Communication Performance & Polling Optimization

## 1. Проблема накладных расходов протокола S7Comm

При наивной реализации опроса ("1 тег = 1 сетевой запрос"):
- Для чтения одного 4-байтового значения `REAL` передается:
  - TCP/IP заголовок: ~ 40 байт.
  - TPKT заголовок (RFC 1006): 4 байта.
  - COTP DT заголовок: 3 байта.
  - S7Comm Request заголовок + Parameter: 14 байт.
  - S7Comm Response заголовок + Parameter + Data header: 15 байт.
- **Итого:** ~ 76 байт накладных расходов на каждые 4 байта полезных данных (эффективность ~ 5%).
- Для 1000 тегов при опросе 100 ms потребуется 10 000 сетевых пакетов в секунду, что приведет к перегрузке коммуникационного процессора (CP) контроллера и срыву цикла опроса.

## 2. Стратегия пакетной оптимизации (PDU Batching & Range Merging)

Драйвер `plc-s7` реализует двухуровневый алгоритм оптимизации запросов:

### Уровень 1: Объединение непрерывных диапазонов (Range Merging)
Если теги расположены в одном блоке данных (DB) или области памяти (Merker, Inputs, Outputs) с небольшим интервалом (GAP <= 16 байт), драйвер объединяет их в единый непрерывный диапазон `Read Area`:

```text
Тег 1: DB100,REAL0   (байты 0..3)
Тег 2: DB100,REAL4   (байты 4..7)
Тег 3: DB100,INT10   (байты 10..11)   [GAP = 2 байта (8..9)]
Тег 4: DB100,REAL12  (байты 12..15)

Наивный подход:  4 сетевых запроса
Оптимизированный подход: 1 запрос диапазона DB100, байты 0..15 (длина = 16 байт)
```

Накладные расходы на передачу 2 "пустых" байт (8..9) составляют 2 байта, в то время как отправка отдельного запроса потребовала бы дополнительных 76 байт служебного сетевого трафика.

---

### Уровень 2: Multi-Variable Batching (до 20 несвязанных элементов в PDU)
Если диапазоны расположены далеко друг от друга (например, `DB100.DBD0` и `DB200.DBD500`), они упаковываются в один PDU `Function 0x04 Read Var` с несколькими элементами `Item Description`:

```text
+-----------------------------------------------------------------------------------+
| S7 Header (10 байт) | Parameter Header (2 байта: Function 0x04, Item Count = N)   |
|   ├── Item 1 Spec (12 байт): DB100, offset 0, len 16                              |
|   ├── Item 2 Spec (12 байт): DB200, offset 500, len 8                             |
|   └── Item 3 Spec (12 байт): Merker, offset 0, len 4                              |
+-----------------------------------------------------------------------------------+
```

## 3. Расчет максимального размера PDU и лимитов

### Формулы расчета емкости PDU:
- **Размер ответа Read Var Response:**
  $$\text{Response Size} = \text{S7 Header (12)} + \text{Param Header (2)} + \sum_{i=1}^{N} \left( \text{Item Header (4)} + \text{Data Length}_i + \text{Padding} \right)$$
- **Для S7-300 / S7-1200 (PDU = 240 байт):**
  - Максимальная полезная длина непрерывного чтения: $240 - 18 = 222 \text{ байта}$.
- **Для S7-1500 (PDU = 960 байт):**
  - Максимальная полезная длина непрерывного чтения: $960 - 18 = 942 \text{ байта}$.

## 4. Спецификация нагрузочных бенчмарков

Сервер тестируется по следующим профилям нагрузки:

| Профиль | Количество тегов | Структура размещения | Целевая частота | Допустимый сетевой джиттер |
| :--- | :--- | :--- | :--- | :--- |
| **Profile A (Small)** | 100 тегов | 1 DB (непрерывный блок) | 100 ms (10 Hz) | $\le 5\text{ ms}$ |
| **Profile B (Medium)** | 500 тегов | 2 DB + Merker (смешанные) | 200 ms (5 Hz) | $\le 10\text{ ms}$ |
| **Profile C (Large)** | 1000 тегов | 5 DB (блочные диапазоны) | 500 ms (2 Hz) | $\le 20\text{ ms}$ |
| **Profile D (High-Density)**| 5000 тегов | 10 DB (промышленный масштаб) | 1000 ms (1 Hz) | $\le 50\text{ ms}$ |

## 5. Метрики производительности (Diagnostics Export)
Драйвер непрерывно собирает и экспортирует через REST эндпоинт `/api/diagnostics` следующие метрики:
- `pollCycleDurationMs`: фактическое время выполнения полного цикла опроса.
- `pduPerCycle`: количество сформированных и отправленных PDU-пакетов за цикл.
- `bytesReadPerSecond`: объем полезных данных, считываемых в секунду.
- `networkErrorsTotal`: счетчик сбоев сокета, таймаутов и ошибок адресации.
- `cacheHitRatio`: процент попаданий в кеш при чтении через REST/WebSocket.
