# Industrial Security & Network Isolation Specification

## 1. Анализ угроз протокола S7 Communication (Threat Modeling)

Классический протокол S7 Communication (ISO-on-TCP, порт 102) создавался в эпоху изолированных технологических сетей и обладает следующими встроенными уязвимостями:

1. **Открытый текст (Plaintext Communication):** Все технологические данные, уставки, команды и аварийные статусы передаются без криптографического шифрования. В случае несанкционированного подключения к сети трафик может быть легко перехвачен анализаторами (например, Wireshark).
2. **Отсутствие аутентификации узлов:** Контроллер не проверяет цифровую подпись или учетные данные подключающегося клиента. Любое устройство, отправившее валидный пакет ISO-on-TCP COTP Connection Request к порту 102, получает доступ к чтению и записи (при включенном PUT/GET).
3. **Отсутствие разделения прав на уровне DB:** В классическом S7Comm невозможно настроить ACL (списки контроля доступа) на отдельные блоки данных (например, разрешить чтение DB100, но запретить запись в DB200). Включение PUT/GET открывает полный доступ ко всем non-optimized DB контроллера.

## 2. Архитектура сетевой изоляции (Network Segmentation)

Для гарантированного предотвращения несанкционированного доступа к технологическому оборудованию применяется строгая трехуровневая модель сегментации (в соответствии со стандартами ISA/IEC 62443):

```text
+-------------------------------------------------------------------------------+
|                      Zone 3: Enterprise & Operator Network                     |
|                                                                               |
|   Web Browser (Operator PC)          Web Browser (Tablet/Mobile)              |
|        [192.168.10.50]                    [192.168.10.51]                     |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼ HTTPS (Port 443) / WSS (Port 443)
+-------------------------------------------------------------------------------+
|                       Zone 2: DMZ / SCADA Server Network                      |
|                                                                               |
|                     PLC Communication & SCADA Server                          |
|                       IP (DMZ): [192.168.10.10]                               |
|                       IP (PLC Net): [10.10.1.10]                              |
|                                                                               |
|   - Authentication (JWT / Session)     - Write Enable Guard                   |
|   - Strict Address & Range Validation  - Complete Audit Trail                 |
+-------------------------------------------------------------------------------+
                                      │
                                      ▼ Industrial Ethernet (TCP Port 102 ONLY)
                                      │ [Firewall Rule: Allow 10.10.1.10 -> PLCs]
+-------------------------------------------------------------------------------+
|                        Zone 1: OT / PLC Control Network                       |
|                                                                               |
|     S7-300 CPU 315       S7-1200 CPU 1214C        S7-1500 CPU 1515            |
|      [10.10.1.20]          [10.10.1.21]             [10.10.1.22]              |
+-------------------------------------------------------------------------------+
```

### Правила межсетевого экрана (Firewall Rules):
1. **Правило 1:** Запретить весь прямой трафик из Zone 3 (клиентские браузеры, корпоративная сеть) в Zone 1 (PLC network).
2. **Правило 2:** Разрешить входящий трафик на SCADA-сервер (Zone 2) только по портам `443` (HTTPS) и `80` (HTTP -> HTTPS redirect).
3. **Правило 3:** Разрешить исходящий трафик с IP-адреса SCADA-сервера (`10.10.1.10`) в Zone 1 только на TCP-порт `102` и только к авторизованным IP-адресам контроллеров.
4. **Правило 4:** Запретить любые входящие подключения к контроллерам с любых других IP-адресов.

## 3. Политика безопасности записи данных (Write Safety Policy)

HMI-сервер является системой диспетчеризации и **НЕ является системой противоаварийной защиты (ПАЗ / Safety)**. 
Любое аварийное отключение или блокировка должны быть аппаратно и программно реализованы внутри самого PLC (Fail-safe логика).

### Реализованные защитные механизмы сервера:
1. **Глобальный флаг разрешения записи (`WRITE_ENABLED`):**
   - По умолчанию переменная окружения установлена в `WRITE_ENABLED=false`.
   - Сервер отклоняет любые запросы на изменение данных на уровне ядра.
2. **Флаг безопасной эмуляции (`DRY_RUN_MODE`):**
   - Позволяет полностью тестировать Web-интерфейс и API, эмулируя успешную запись без отправки пакетов в PLC.
3. **Декларативное ограничение тегов (`allowWrite: true`):**
   - Тег, не имеющий явного флага `allowWrite: true` в конфигурации YAML, отклоняется сервером со статусом `403 Forbidden / WRITE_NOT_ALLOWED_FOR_TAG`.
4. **Валидация диапазонов значений (`minValue` / `maxValue`):**
   - Каждое записываемое значение проверяется на соответствие допустимому физическому диапазону до формирования сетевого пакета.
5. **Аудит и протоколирование:**
   - Все попытки записи (как успешные, так и отклоненные) фиксируются в журнале аудита безопасности со следующими атрибутами:
     - `timestamp`: точное время UTC.
     - `clientId` / `user`: идентификатор сессии / пользователя.
     - `plcId` / `tagId`: идентификатор контроллера и тега.
     - `address`: физический S7-адрес (например, `DB100.DBD4`).
     - `oldValue` / `newValue`: предыдущее и новое значение.
     - `status`: результат (`SUCCESS`, `REJECTED_OUT_OF_BOUNDS`, `REJECTED_GLOBAL_DISABLE`, `TIMEOUT`).

## 4. Рекомендации по организации блоков данных в PLC

1. **Разделение DB чтения и записи:**
   - Рекомендуется выделять отдельный блок данных для телеметрии (например, `DB100_HMI_Read`) и отдельный блок данных для команд/уставок (например, `DB101_HMI_Write`).
2. **Квитирование команд (Handshake Bit Pattern):**
   - При передаче команд управления запись производится в регистр команды со взводом бита запроса (`bRequest := TRUE`).
   - Логика PLC после верификации условий безопасности выполняет действие, сбрасывает бит запроса и выставляет бит подтверждения (`bDone := TRUE`).
